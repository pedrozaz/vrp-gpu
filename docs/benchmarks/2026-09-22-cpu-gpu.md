# CPU/GPU validation — 2026-09-22

## Result

All delta, selection and independent reversal-cost checks passed for nine
synthetic cases and ten routes constructed from Solomon C101 (100 customers).
The GPU public API was slower than the CPU reference for every measured route
with at least two customers. These results describe current API latency; they
do not isolate kernel throughput or establish a general GPU crossover size.

The run produced [380 raw sample pairs](2026-09-22-cpu-gpu.csv): 20 per route,
after three warmups per backend. See the [protocol](cpu-gpu-validation.md) for
exact correctness tolerances, ordering, generation and measurement boundaries.

calculating statistics from the CSV.

## Cost validation and interpretation

For C101, the constructed CVRP solution has ten routes and f64-summed matrix
cost 1311.4998662471771. Applying exactly one selected move per route gives
1279.676985502243, with nine improving routes. CPU and GPU selected the same
indices. These are full-precision Euclidean matrix costs, not rounded reference
benchmark costs. They are not converged solutions or comparisons with published
Solomon best-known results, and time-window feasibility is not claimed.

At 2048 customers the measured CPU median is 25.52 ms versus 156.17 ms on the
GPU path (CPU/GPU ratio 0.1634). This is evidence against a speedup claim for
the current end-to-end selection API in this workload. Repeated validation,
context/module setup, allocation and transfers are included on the GPU path;
the experiment does not attribute their individual costs. Reusing device state
or changing kernels would need a separate optimization branch and measurement.

Only one real instance from the C1 family was used. C2, R1, R2, RC1 and RC2,
solver convergence and external `vrp-cli` comparisons are not covered by this
report. Synthetic stress fixtures must not be interpreted as those families.
